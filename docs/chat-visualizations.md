# Inline chat artifacts

For notifications, progress, plans, multipart tool results, JSON inspection and
anchored citations, see [Rich chat events and results](chat-rich-content.md).

The chat can display self-contained HTML visualizations generated by any of its providers.
This feature is local presentation: it does not publish files to a third-party service.
Chrome and Exchange receive the registered content through their existing authorized chat
snapshot transports, rather than attempting to open an executor-side path.

## Agent workflow

Each prompt includes a conversation-specific directory:

```text
<working-folder>/.ai-browser/visualizations/<conversation-scope>/
```

Write a completed `.html` or `.htm` file directly in that directory, then call:

```json
{ "path": "/absolute/path/to/conversation-scope/chart.html", "title": "Sales by month" }
```

The tool is `chat_present_html`. It requires the chat's conversation capability and cannot
choose another conversation. Calling it again with the same path revises the existing card.
It returns an ID and content revision; no additional output reference is required.

For providers without the tool, a standalone assistant line also works:

```text
visualize{"path":"/absolute/path/to/conversation-scope/chart.html","title":"Sales by month"}
```

The parser accepts the optional `mode: "wide"` field. Quoted examples, fenced or indented
code, incomplete markers, arbitrary JSON, and ordinary HTML links stay inert. Both adapters
use the same file checks and snapshot archive. Existing native markers pointing elsewhere
are refused; move the source into this conversation's supplied directory first.

Use inline CSS/JavaScript, SVG, canvas or browser-native MathML. External scripts, images,
fonts and stylesheets, network requests, popups, forms, downloads and host actions are not
enabled. The native OpenAI Visualize skill's CDN and runtime assumptions are broader than
this implementation; generate a self-contained version when a reference needs them.

## Images

The same conversation directory also accepts PNG, JPEG, GIF and WebP images up to
4 MB each. Copy the completed image directly into that directory, then call:

```text
chat_present_image({"path":"/absolute/path/to/conversation-scope/cat.png","title":"Cat"})
```

Providers without the tool can emit a standalone assistant line:

```text
image{"path":"/absolute/path/to/conversation-scope/cat.png","title":"Cat"}
```

The prompt includes both workflows. Native image cards have Expand/Collapse controls
and do not run an iframe. Reusing a path updates its card; text surrounding a card can
stream without replacing its image element. Publication snapshots the binary, so the
card survives deletion of the original file and conversation restoration. History stores
only references. VS Code, Chrome and Exchange receive the archived content through the
existing snapshot transport; client browsers do not need access to the source file.

The host checks the file signature instead of trusting its suffix. SVG, remote URLs,
linked files, files outside this conversation's directory, and oversized files are
refused. Images returned by arbitrary provider tools are not automatically rendered:
the agent must publish the saved file through the tool or marker above.

## Files, tables, sources and media

All tools take `{path, title?}` and use the same conversation directory, immutable
archive, update behavior and cross-surface snapshot transport as images:

| Tool | Output | Input |
| --- | --- | --- |
| `chat_present_file` | Download card | Any completed file, up to 4 MB; served as a download rather than executed |
| `chat_present_table` | Searchable, sortable table with 100 rows per page | UTF-8 JSON, up to 1 MB |
| `chat_present_sources` | Source cards with title, URL and description | UTF-8 JSON, up to 1 MB |
| `chat_present_audio` | Native audio player and download | MP3, WAV, OGG, M4A or WebM, up to 4 MB |
| `chat_present_video` | Native video player and download | MP4 or WebM, up to 4 MB |

Table JSON has this shape:

```json
{"columns":["Name","Value"],"rows":[["Example",42],["Missing",null]]}
```

Use 1–100 string column labels and at most 10000 rows of matching length. Cells can
be strings, finite numbers, booleans or null. Downloads preserve the original JSON.
Filtering and sorting happen locally; row content is displayed as text.

Sources JSON is an array:

```json
[{"title":"Reference","url":"https://example.com/reference","description":"Optional context"}]
```

At most 100 sources are accepted. URLs must be HTTP(S) without credentials. Links
open only on a user click. The tool displays supplied sources; it does not fetch or
verify them. Titles and descriptions never execute HTML.

Without MCP, use a standalone `file`, `table`, `sources`, `audio` or `video` marker,
followed immediately by its JSON reference. Native private-use delimiters also work:

```text
table{"path":"/absolute/path/to/conversation-scope/table.json","title":"Results"}
video{"path":"/absolute/path/to/conversation-scope/clip.webm","title":"Demo"}
```

Claude Code and Codex receive the same output instructions. Claude's MCP names use
the `mcp__ai-browser__` prefix, for example `mcp__ai-browser__chat_present_table`.
Claude can use plain ASCII markers if its output drops private-use delimiters.
Protocol integration tests exercise both providers; no generation API is added by
these presentation tools.

In VS Code, Download opens the editor's Save dialog and resolves only an archived
revision referenced by that conversation. In Chrome and Exchange, a user click
creates a local Blob download. Media uses local Blob URLs, without autoplay or
network fetching; codecs depend on the viewer's browser. Unsupported codecs show a
download fallback. Removed or revised media releases its player and Blob URL.
Large files and longer videos currently need a smaller export: the transport is
bounded to 4 MB per binary file and 6 MB of active presentation snapshots.

## Revisions and interaction state

An explicit publication snapshots a completed file. Already registered references also
refresh after tool completion and at turn end, so an agent can revise a view while it works
without executing every file append. There is no background file watcher. A failing update
keeps the last successful snapshot and displays the error.

Surrounding assistant text updates without replacing the card or iframe. A different
content hash replaces only the sandbox's inner document. An optional compatibility API
preserves JSON state between those revisions:

```js
const saved = window.openai.widgetState;
// Restore only fields that this visualization understands.
await window.openai.setWidgetState({ value: 37 });
```

State is limited to 16 KB and retained for that mounted card, not persisted across a chat
switch or application restart. Other OpenAI host APIs, including follow-up messages and
tool calls, are not implemented. Pure slider/button interactions can remain entirely local.

Cards have Expand/Collapse and Stop/Run controls. At most eight frames run at once; opening
another pauses the oldest frame, which can be reopened with Run. Detached cards close their message ports
and release their renderer. Missing snapshots do not launch empty execution frames.

## Storage and isolation

Source files are limited to 1 MB of valid UTF-8. The host rejects outside paths, linked
directory components, file symlinks, hard links, non-regular files and changes during reading.
The source directory receives a local `.gitignore`. Snapshots are content-addressed under
the extension's global storage, scoped to the conversation. Stored chat entries contain
references, not HTML, image or artifact data. Saved hashes are verified when loaded from disk.

To bound chat transport and memory, up to eight recent unique snapshots are loaded, with a
6 MB combined budget including serialized file, structured and base64 media data; HTML retains its 2 MB budget. Older content remains archived but can show as unavailable in this
initial implementation. Archived versions currently follow extension-storage retention;
there is no automatic disk quota or archive cleanup UI.

Generated code runs in an opaque-origin sandbox, with no same-origin permission or chat
API. A packaged wrapper enforces an additional CSP on its inner view and receives only
bounded resize, widget-state and error reports. The wrapper's `frame-src about:` also blocks
HTTP navigation of the generated document, including navigation back to the chat origin.
The main chat keeps its nonce script policy. Trusted host delivery and visualization
messages use separate channels.

This is browser isolation, not a hard CPU/memory quota or a general-purpose offline VM.
Do not pass credentials or chat transport tokens to generated content. Platform-specific
runtime verification remains appropriate when updating Chromium, VS Code or MV3 policies.

## Validation

```sh
npm run compile
npm run typecheck
npm run build-chrome
node exchange-server/scripts/build-chat.mjs
node --test src/chat/visualizationProtocol.test.ts src/chat/visualizationStore.test.ts src/chat/visualizationIntegration.test.ts
node scripts/test-visualizations-browser.mjs
```

The browser probe uses a disposable headless Chrome profile and its own local fixture. It
loads the full chat bundle under a VS Code-style preload that replaces `window.parent`
and `window.top`, then verifies initial and subsequent host snapshots and child rejection. It
checks DOM/storage isolation, forged host messages, blocked fetch/image/script requests and
document navigation, a stable frame during updates, and widget state across code revisions.
It does not install the Chrome extension, reload a user's editor, deploy Exchange, or publish
content. A development-host smoke check in each target client is still useful before release.
